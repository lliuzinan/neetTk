## Source and rights gate

- Official resources may be consulted for factual validation; public access does not automatically authorize commercial republication, adaptation, PDF bundling or hosting.
- Record actual source terms and evidence. Do not infer permission from a citation, a free download, a third-party mirror or historical license assumptions. Check the exact OpenStax version/license, including noncommercial restrictions.
- NCERT's published terms also discuss linking permissions. Verify the intended use before adding a new official-resource link package. When unresolved, keep the public page in draft and give the owner a concrete permissions question. Continue independent original worksheet/layout work instead of inventing permission.
- NTA references require exact year, paper code, question identifier and the final revised answer key where relevant. Do not label coaching reconstructions or CBSE samples as NEET official questions.
- Original examples require explicit assumptions and source-backed reasoning, with independent review where promised. Do not relabel generated exercises as sourced questions. Prefer an original blank reasoning worksheet for this phase.
- Any future licensed question supplier must explicitly cover web display, advertising-supported use, adaptation and printable distribution. Do not purchase or accept contract terms automatically.
- Useful starting points to verify: https://ncert.nic.in/exemplar-problems.php?ln=en ; https://nta.ac.in/NoticeBoardArchive ; https://cbseacademic.nic.in/ ; https://openstax.org/books/biology-2e/pages/preface . Discovery links are not a license grant.

## Daily operating rules

1. Read this plan, the current Git status, repository instructions, latest release records, and relevant writing/illustration/PDF skills. Inspect current production and code before assuming an old audit issue still exists.
2. Choose one bounded deliverable; update its status as work progresses. Prioritize correctness, permissions and real usability over a date or number of pages.
3. Keep a source register with: source owner, title, version/date, chapter/question ID, URL, verified answer/reasoning, syllabus scope, reuse terms, intended use, verification date, and unresolved permission/reviewer actions.
4. For code/content changes, run focused checks plus the project build/tests as appropriate. Check responsive screenshots and keyboard behavior for affected pages. For PDF work use the PDF skill and render all pages.
5. Keep credentials, personal data and unpublished drafts out of reports. Do not submit dummy production leads, alter account/payment settings or buy content.
6. Follow the existing authorized release workflow only when quality and rights gates pass. Report separately: edited, tested, committed/pushed, deployed, publicly verified. Never describe a local build as live.
7. Log completion evidence and the next item below. Notify for a completed meaningful deliverable, failure, or owner action; remain quiet for unchanged/non-actionable states.
8. After all milestones are complete, do not start daily article production again. Report completion and propose a new bounded phase; subsequent runs can perform a small regression/source check and stay quiet when nothing changes.
